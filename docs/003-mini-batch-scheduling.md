# ADR 003: 스케줄링 방식으로 미니배치(cron) 채택

**날짜**: 2026-04-19
**상태**: Accepted (v1 기준)
**결정자**: 주찬

## 맥락

데이터 수집 및 처리의 스케줄링 방식 선택. 후보:

1. **실시간 스트리밍** (Kafka + Flink / Redpanda + Bento)
2. **미니배치** (cron 또는 Airflow, 15~60분 주기)
3. **일배치** (매일 1회)

## 결정

**미니배치 (cron, 매 30분)** 선택. v1 기준.

## 근거

1. **데이터 소스 특성** — Reddit, 인벤, 디시의 글/댓글은 초 단위로 쏟아지지 않음.
   분당 수 건 수준. 스트리밍이 주는 latency 이점이 무의미.

2. **LLM API 호출 지연** — Gemini 호출 2~5초. 스트리밍 파이프라인을 만들어도
   병목은 LLM. 실시간 처리 의미 없음.

3. **인프라 복잡도 vs MVP 완주** — Kafka/Flink는 학습+운영 비용이 크고
   첫 DE 프로젝트 완주 확률을 떨어뜨림. cron은 30초 안에 설정 가능.

4. **사용자 체감 차이 없음** — 여론 변화는 분~시간 단위로 움직임.
   "15분 전 데이터"와 "실시간"의 체감 차이 없음.

5. **비용 관리 용이** — 정해진 간격에 정해진 양만 처리하므로 LLM API 비용
   예측 및 제어 쉬움.

6. **진화 스토리 만들기** — v1 cron → v2 Airflow 전환 회고가 좋은
   면접 자료가 됨. ("스케줄 복잡도가 증가해서 Airflow로 마이그레이션했다")

## 대안을 선택하지 않은 이유

**실시간 스트리밍:**
- 데이터 빈도가 스트리밍 인프라 정당화하기엔 낮음
- LLM이 병목이라 스트리밍 이점 희석
- Kafka 운영 경험 없어 완주 리스크 큼
- 포트폴리오에 "Kafka 써봤다"는 불필요한 과장 욕망은 경계해야 함

**일배치:**
- "급변하는 여론 실시간 감지"라는 핵심 가치 훼손
- 긴급 이슈(터진 패치 불만 등)를 하루 늦게 감지하면 무용지물

## v1 세부 설계

```
cron 스케줄:
*/30 * * * *   uv run python pipeline/scripts/run_pipeline.py
```

수집 주기를 소스별로 다르게:
- Reddit API (가벼움): 매 30분
- 인벤/디시 (HTML 크롤링 무거움): 매 60분 (Week 2에서)
- YouTube (할당량 관리): 매 6시간 (Week 3에서)

## v2에서 Airflow로 전환할 조건

- 소스 3개 이상 되어 스케줄 관리 복잡해졌을 때
- 실패 재시도/알림 로직이 필요해졌을 때
- DAG 시각화로 파이프라인 설명할 필요가 있을 때 (포트폴리오/면접)

## 결과 및 위험

**긍정**:
- 1주차 완주 가능한 복잡도
- 비용 예측 가능
- 운영 단순

**위험 및 대응**:
- 본인 PC가 꺼지면 수집 중단 → v2에서 Cloudflare Workers Cron 또는
  라즈베리파이/VPS 이전 검토
- cron 로그 관리 번거로움 → 파이프라인 내에서 파일 로깅 + 실패 알림
  (추후 Discord/Slack webhook)
